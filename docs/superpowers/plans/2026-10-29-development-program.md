# برنامج تطوير بورحان — من الإصلاح إلى التشغيل المؤسسي — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

**Goal:** نقل بورحان من نظام مُصلَح ومخضّر على CI إلى نظام مُشغَّل فعلياً: إثبات مغلق بأدلة بناء نهائية، تدقيق أمني مستقل، بنية إنتاج حقيقية، بيانات حقيقية للبحث، تجربة مؤسسية 30 يوماً موقّعة، ثم المرحلة التجارية.

**Architecture:** لا تغيير معماري جذري — البنية أثبتت صحتها في الإصلاح (حوكمة مغلقة الفعل، هوية موثقة، عزل RLS، مخزن مشفر، توقيع Ed25519، محقق V3، عامل تثبيت حقيقي). التطوير يُرحّل المكونات من "صحيح محلياً" إلى "موثوق إنتاجياً": PostgreSQL حقيقي، OIDC إنتاجي، KMS/HSM خلف واجهة KeyProvider القائمة، مراقبة قابلة للقياس، ثم بيانات حقيقية وتجربة موقعة.

**Tech Stack:** كما هو دون ترقيات إطارية — Solidity 0.8.20/Hardhat 2، Python/FastAPI/SQLAlchemy، PostgreSQL 16، React 18/Vite 5، Docker، Playwright. الجديد: مزود OIDC إنتاجي، KMS/HSM، Prometheus/Grafana، أدوات SCA.

**Spec:** نفس عقد التصميم الملزم [2026-10-23-verified-remediation-design.md](../specs/2026-10-23-verified-remediation-design.md) + [خطة المرحلة التجارية الأصلية](2026-10-22-phase-4-commercial-readiness.md) بعد DG4. هذا البرنامج لا يعدّل عقد V2/V3 ولا مخطط القاعدة إلا بمهاجرات مُراجعة.

**Spec note:** هذه الخطة مرحلة تطوير/تشغيل وليست إصلاحاً — عقد التصميم §3 يبقى ملزماً حرفياً، وكل ما هو "مقترح" هنا يمر بمراجعة قبل التنفيذ كالمعتاد.

## Global Constraints

- استمرار نظام الأدلة الصادقة: لا بيانات مؤسسية مصطنعة، لا ادعاء تدقيق دون تدقيق، لا ادعاء تجربة دون تجربة، ولا تفعيل ML دون بوابة. findings.csv يستمر كسجل الوثائق الموحد.
- لا نشر عقود جديدة على شبكة عامة ولا أموال حقيقية قبل إغلاق التدقيق الأمني الخارجي (H02) وإصلاح نتائجه.
- المفاتيح الحقيقية لا تدخل Git أو ZIP أو logs أو الحاويات إطلاقاً؛ المحلي يبقى بـsecret mounted خارج المستودع.
- SQLite يبقى demo/اختبار فقط؛ أي تشغيل مؤسسي على PostgreSQL 16 حصرياً.
- البيانات الحقيقية للمحث تخضع تقليل البيانات والخصوصية (لا PII خارج نطاق المعالجة، اتفاقية استخدام موقعة) ولا تُرفع لأي مكان عام.
- تعديلات المستخدم غير الملتزمة تُحترم كالسابق؛ لا git add شامل؛ commit محصور بملفات المهمة.
- RPO/RTO وحدود الحمل تُقاس ولا تُعلن محققة قبل القياس؛ PILOT_NOT_STARTED حتى وجود جهة حقيقية.

## Review Focus

1. مزود KMS يعيد مفتاحاً خاطئاً للمؤسسة — H06 يفشل الإغلاق ولا يخدم مفتاحاً مشتركاً.
2. ترقية PostgreSQL تكشف فروقات SQLite المخبأة — H04 يفشل بصدق ويصلح، لا يخفي.
3. بيانات حقيقية تُدخل عبر مسار تجاوز بيانات التدريب — H09 يطبق الفصل الزمني حرفياً على البيانات الحقيقية نفسها.
4. ادعاء "مُدقَّق" قبل وصول تقرير المدقق — H02 يمنع أي ذكر للمدقق قبل استلام التقرير الموقع.
5. تجربة 30 يوماً تبدأ دون توقيع — H11 يبقي PILOT_NOT_STARTED حتى التوقيع الحقيقي.

## بوابات البرنامج

- **DG0 — إثبات مُغلق:** إعادة `npm run remediation:check` على البناء الأخضر الحالي؛ تحويل صفوف findings.csv المؤهلة إلى VERIFIED_FIXED بأدلة البناء الجديد؛ توثيق ما تبقى.
- **DG1 — تدقيق مُغلق:** تقرير تدقيق عقود خارجي موقع + إصلاح نتائجه باختبارات انحدار + إعادة تدقيق المتابعة إن لزم؛ اختبار اختراق API وتقريره.
- **DG2 — إنتاج مُصلَب:** بيئة staging على PostgreSQL حقيقية + OIDC إنتاجي + KMS خلف KeyProvider + مراقبة/alerts + تدريب استعادة مُقاس.
- **DG3 — بحث حقيقي:** تجربة بحث على بيانات مؤسسية حقيقية بالبوابات نفسها؛ قرار ML مُوثق (تفعيل أو نتيجة سلبية صادقة).
- **DG4 — تجربة موقعة:** 30 يوماً مع جهة حقيقية، سجل حوادث، مراجعة أسبوعية، توقيع بشري حقيقي.
- **DG5 — المرحلة التجارية:** الانتقال لخطة 22 أكتوبر (فوترة، منظّم، تقارير امتثال) بعد تقرير التجربة.
