# Runbook: BurhanHTTP5xxRatioHigh — engine 5xx ratio above 1% (5m)

**Alert:** `BurhanHTTP5xxRatioHigh` — `sum(rate(burhan_http_responses_total{code=~"5.."}[5m])) / sum(rate(burhan_http_responses_total[5m])) > 0.01`, `for: 1m`.
**Severity:** critical. **Owner:** Operations (H07). **Source of truth:** `burhan_http_responses_total` — counted by the engine's no-PII middleware with ROUTE-TEMPLATE labels only (`/api/v2/cases/{case_id}` style; no raw URLs, no identifiers).

## Meaning

More than 1% of engine responses over the last 5 minutes are server errors.
Route-template breakdown in the metric tells you WHERE without exposing any
request content.

## First response (10 minutes)

1. Identify the failing routes:
   `http://127.0.0.1:19090/api/v1/query?query=topk(10,sum by (path,code)(rate(burhan_http_responses_total{code=~"5.."}[5m])))`
2. Read the unhandled-exception tracebacks — the engine persists them next to
   its working directory: `docker exec aml_staging_engine sh -c "tail -200 unhandled-exceptions.log"`
3. Correlate with dependency health on the H07 dashboard:
   - `burhan_metrics_db_up` / readiness 503 panel → database or KMS/vault.
   - `burhan_rpc_probe_success` → EVM RPC (evidence verification paths).
4. Single-route 500 spikes right after a deploy → roll the engine back
   (`docker compose ... up -d --build ai-engine` with the previous revision);
   broad 500s with DB errors → PostgreSQL first.

## If it is not the engine

A 502/504 generated by nginx in FRONT of the engine is not counted here
(the middleware sees only engine responses) — if users report errors but this
alert is quiet, check `aml_staging_frontend` / nginx logs.

## Verification after recovery

- 5xx ratio panel returns below 1% and the alert resolves.
- No new entries appended to `unhandled-exceptions.log`.
