## 1. What was implemented

### 1.1 Persistence — `wallet_challenges` table + repository

- **`ai-engine/app/db/models.py`** — new `WalletChallengeModel` (table `wallet_challenges`):
  `id` (challenge uuid), `institution_id` (tenant FK → institutions, CASCADE), `sub`,
  `wallet_address`, `domain`, `chain_id`, `nonce` (**globally UNIQUE**), `message`,
  `issued_at`, `expires_at`, `consumed_at` (single-use marker). Added to `RLS_TABLES`
  (16th institutional table) per the R11 §6 checklist.
- **`ai-engine/app/db/migrations/versions/institutional_wallet_challenges.py`** —
  revision `institutional_wallet_challenges`, `down_revision = "r11_baseline"` (the sole
  head at merge time, see §6). PostgreSQL section: ENABLE + FORCE RLS +
  `tenant_isolation_policy` (USING + WITH CHECK on the transaction-local
  `app.current_institution_id`), exactly the baseline pattern. App-role DML grants flow
  from `ALTER DEFAULT PRIVILEGES FOR ROLE ira_aml_migrator` (already provisioned).
  SQLite (dev/demo) section: same table, no RLS.
- **"One active wallet per membership"** — enforced by the existing R11-baseline unique
  constraint `uq_wallet_binding_institution_sub` on `wallet_bindings` (a rotation
  REPLACES the active row; `save_binding` upserts) and pinned by
  `test_one_active_wallet_per_membership_constraint` on real PostgreSQL
  (second active row per membership → `IntegrityError`). A global unique on
  `wallet_address` was deliberately NOT added: the R11 suite legitimately binds the same
  synthetic address under two tenants, and the R02 wallet-rebinding rule is enforced in
  the service (`wallet_bound_elsewhere` → "Wallet already bound to another institutional
  identity").
- **`ai-engine/app/repositories/wallet_binding_repository.py`** (new) —
  `WalletBindingRepository` with `save_challenge / get_challenge /
  consume_challenge / save_binding / get_binding / wallet_bound_elsewhere`.
  **`consume_challenge(session, challenge_id, institution_id, sub, now)`** is the brief's
  fixed interface and is a single atomic compare-and-swap UPDATE:
  `... WHERE id = :cid AND institution_id = :inst AND sub = :sub AND consumed_at IS NULL
  AND expires_at > :now` — rowcount 0 → `ValueError("Challenge already used or expired")`.
  On PostgreSQL the UPDATE row lock serializes racing sessions (the `consume_once_two_sessions`
  test uses two distinct physical connections). `ChallengeRecord`/`BindingRecord` moved
  here (no import cycle); both re-exported by the service module.

### 1.2 Service — `app/security/wallet_binding.py`

- `WalletBindingService(repository=None, domain, default_chain_id, ttl_seconds=300,
  chain_reader=None, session_factory=None)`; the DEFAULT repository is now the DB
  repository (the brief: replace `InMemoryWalletBindingRepo` on institutional paths —
  the in-memory double remains, clearly marked UNIT-TEST-ONLY).
- `create_challenge(session, identity, request, ttl_seconds=None)` persists the challenge
  (300s TTL default) inside the transaction-local tenant context.
- `verify_and_bind(session, identity, request)` — strict fail-closed ordering:
  1. **Transaction 1:** fetch challenge → tenant/subject/domain/chain checks →
     **atomic CAS consumption (commits BEFORE signature verification**, so a failed
     proof burns the challenge — no signature brute-forcing on a live challenge);
  2. EIP-191 signature recovery must equal the challenge wallet;
  3. **the single on-chain RoleManager read** (`getParticipant(wallet)`) — only reached
     after every local proof; unknown/inactive/zero-id wallets →
     "Wallet is not an active participant on-chain (unknown, rotated, or revoked)";
     a wallet bound to a different participantId → rejected; on-chain role must agree
     with the membership role; binding stores the CHAIN participantId + generation;
  4. **Transaction 2:** wallet-not-bound-elsewhere check + upsert of the single active binding.
- `get_active_binding(institution_id, sub) -> BindingRecord | None` — the brief's fixed
  interface; opens its own short session and wraps it in `tenant_transaction` (so the
  read is RLS-scoped) when the repository is DB-backed.
- `verify_on_chain_authorization(identity)` + route dependency
  **`require_on_chain_authorization(*roles)`** (in `routes/v2/identity.py`) for R07/R12
  sensitive writes: no binding → 403; **authorization (license) read failure →
  `ChainUnavailableError` → 503** — never a fallback to browser claims; stale on-chain
  generation / participantId / role mismatch → 403.
- `RoleManagerChainReader` — real `eth_call` implementation of the R02
  `getParticipant(address) -> (bytes32, uint256, Role, bool)` read (keccak selector via
  `eth_utils`, ABI word decoding, Role enum mapping 0..4), transport injectable for tests.
- Singleton accessors `get_wallet_service`/`set_wallet_service` moved here; the routes
  re-export them (existing test imports keep working).

### 1.3 OIDC — `app/security/oidc.py`

- `OIDCVerifier(..., algorithms=["RS256"], clock_skew_seconds=60)`: the **algorithm
  allowlist is checked on the unverified header FIRST** (alg-confusion impossible);
  `jwt.decode(..., leeway=60, options={"require": ["exp","iat","nbf","sub","aud","iss"]})`
  plus an explicit mandatory-claim sweep (`exp`/`iat`/`nbf`/`sub` non-empty) so the
  invariant does not depend on the PyJWT version.
- **`verify_token` now returns the VERIFIED CLAIMS dict** — it derives no role and no
  identity object. Failures split: `ValueError` → 401 (bad token) vs
  `OIDCProviderError` → 503 (JWKS/provider unreachable, incl. `PyJWKClientError`).
- `MockJWKSProvider` stays as the test fixture (synthetic per-run RSA keys only).

### 1.4 Membership-sourced identity — `app/repositories/institution_repository.py`

- **`resolve_identity(session, claims) -> Identity`** (brief interface): looks up
  `memberships` under the transaction-local tenant context; **no active membership →
  `MembershipResolutionError` (403)** — a JWT can neither create a membership nor grant
  a role; the JWT role claim is ignored entirely (it routes nothing, authorizes nothing);
  unknown stored role strings → `RoleEnum.NONE` (fail-closed); wallet/participant_id/
  generation overlaid from the stored binding via the wallet service.
- Implementation note (bug found by the integration suite): the membership row is read
  and **snapshotted INSIDE `tenant_transaction`** — after its commit the ORM instance is
  expired and a lazy refresh would re-SELECT without the RLS context (and correctly see
  nothing → `ObjectDeletedError`). Caught RED→GREEN on real PostgreSQL.
- `institution_id` from the token ROUTES the lookup only: authorization requires an
  active membership row under exactly that institution for that subject; a forged
  institution claim yields 403, never access.

## 6. OIDC test approach — honest disclosure

- **Real signed JWTs, synthetic keys**: every token in the suites is a genuine RS256
  JWT signed with an in-test `cryptography`-generated RSA key through `MockJWKSProvider`
  / raw `jwt.encode` — signature verification, iss/aud/exp/iat/nbf/leeway and the
  mandatory-claim path all execute for real through PyJWT.
- **A real external OIDC server was NOT run.** The verifier's live-JWKS path
  (`PyJWKClient` over HTTP) is exercised only in its FAILURE direction
  (`test_demo_identity_absent_when_oidc_provider_fails` points the JWKS URL at a
  connection-refused endpoint and asserts 503 + no demo leak). A full in-test fixture
  issuer (discovery + JWKS endpoint) is explicitly deferred to R14 per the plan; until
  then this is the documented gap.
- **R02 contracts were consumed at the interface level, not against a live chain.**
  `RoleManagerChainReader` implements the real `getParticipant(address)` eth_call
  (selector encoding, 4-word ABI decode, Role mapping) with an injectable transport, but
  no Hardhat/Anvil node was deployed in the test loop; the behavioral tests inject a
  fake reader exposing the same `get_participant(wallet)` interface. The
  "challenge for a wallet not proven participant is rejected before chain reads"
  requirement is implemented (and tested via a spy reader) as an ORDERING guarantee:
  every local proof — challenge validity, tenant, subject, domain, chain id, signature
  recovery, and the atomic CAS consumption — completes before the single on-chain read;
  a wallet failing any local proof never triggers a chain read (spy read-count 0).
- "License read" is interpreted as the on-chain authorization read (RoleManager
  `getParticipant` = the institutional authorization record): `require_on_chain_authorization`
  answers 503 when that read fails and 403 on mismatch — never trusting browser claims.
  There is no separate licensing server in `ai-engine` (grep for "license" is empty).
