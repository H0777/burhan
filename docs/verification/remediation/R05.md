## 1. What changed

- **`shared/python/evidence_crypto.py`** (single source of truth, used by server AND offline verifier):
  - `canonical_bytes(body)` — UTF-8, `sort_keys=True`, `separators=(",",":")`, `ensure_ascii=False`, `allow_nan=False`; floats rejected, duplicate JSON keys rejected at parse time (`parse_strict_json` / `DuplicateJsonKeyError`), no Unicode normalization (Arabic signed as-is).
  - `signature = Ed25519(domain + NUL + canonical_bytes(body))` over the three fixed domains `AML_SERVICE_MANIFEST_V1`, `AML_DOSSIER_V1`, `AML_BACKUP_V1` (`domain_separator` refuses unknown domains). No HMAC, no key derived from `institution_id`, no fallback paths.
  - `SignedEnvelope` = `{body, algorithm:"Ed25519", signature:base64}`; `SignatureResult.status ∈ {verified, invalid, unavailable}` with a fixed reason vocabulary (stable contract for R06/R07/R09/R16).
  - `Signer` / `Verifier` — verifier is fail-closed and uses ONLY the registry public key (embedded key material never trusted); `compromised` invalidates from `invalid_from` (missing `invalid_from` → every signature of that key invalid); `retired` accepted only under an external `trusted_time`; missing registry/key → `unavailable`, never `verified`.
  - `envelope_digest` — sha256 over the canonical form of the FULL envelope (signature included), so a signature-only change alters the digest with an identical body.
  - DEK wrap/unwrap: X25519 (derived from the Ed25519 seed) + HKDF-SHA256 + AES-256-GCM; wrapped form carries ephemeral pubkey/nonce/ciphertext only.
- **`ai-engine/app/security/signing.py`** — loads the shared module from a FIXED path walked up from the distribution layout (refuses caller/ZIP-chosen paths) and re-exports it; `key_provider.py` — `KeyProvider` ABC (KMS-swap isolation) + `LocalFileKeyProvider` (read-only seed files outside the repo, component validation, resolved-path traversal refusal, fail-closed `KeyError`); `trust_registry.py` — `load_registry` (missing/invalid document raises → caller must treat as `unavailable`).
- **`shared/schemas/service-manifest-v1.schema.json`, `trust-registry-v1.schema.json`** — consumable contracts for downstream tasks.
- **`shared/fixtures/signatures-v1.json`** — clearly synthetic fixture (`SYNTHETIC TEST FIXTURE` note); public keys only; generating private key discarded, never committed.
- **`docs/runbooks/key-management.md`** — custody (read-only mounts outside the repository, service-account owned), trust-registry lifecycle (active/retired/revoked/compromised), KMS swap path, logging discipline (no key material in logs).
- **`ai-engine/tests/test_signing.py`** — the 17-test suite below.
- **`ai-engine/requirements.txt` / `requirements.lock` deliberately NOT touched** — `cryptography>=42.0.0` was already declared in `requirements.txt` and satisfied by the runtime (50.0.2), and dependency edits belong to the integration lead per the brief's control notes. ## 2. Historical vulnerability context (why this task exists)

`docs/verification/remediation/baseline-2026-10-23.md:50` (F05, P0): the old `verify-evidence-export` tool accepted a ZIP whose signature was the literal placeholder `INVALID-NO-PRIVATE-KEY` with `algorithm=none`, and there was no trust registry at all — a forged/un-signed dossier verified as genuine. Also documented in `docs/runbooks/key-management.md:12-13`. R05 closes the mechanism: `algorithm` is enforced (`test_algorithm_field_enforced` — `algorithm:"none"` → `invalid`/`unsupported_algorithm`), verification keys come only from the external registry (`test_embedded_key_not_trusted`), and the fail-closed tri-state means "cannot verify" can never be reported as `verified`.

## 5. Digest-sensitivity proof (signature-only change, identical body)

Standalone demonstration (script run from %TEMP%, keys generated at runtime and discarded; also pinned as `test_signature_change_alters_envelope_digest` after the `901c495` fix — re-keying the SAME `(institution_id, key_id)` to a different private key keeps the body byte-identical while the signature changes):

```
bodies_canonical_identical: True
signatures_differ: True
digest_a: 6239fb50d63837bf0b603354312aeb3ef4ebfc4be1be5aace2536b2926913c39
digest_b: a9d243e3e2d98be0c0c00c64fd63df791f4f29688a20bd642dbcf76ee849de31
digests_differ: True
```

Because `envelope_digest` covers the canonical form of the whole envelope, the signature field is inside the digest: swapping the signature (with a byte-identical body) necessarily changes the digest.

## 9. What was NOT tested, and why

- **KMS / remote key-service integration** — the `KeyProvider` ABC exists precisely to isolate that swap (runbook documents the path); `LocalFileKeyProvider` is the interim custodian per spec §6 ("مؤقتاً"), so a live KMS is out of scope and nothing was purchased/built for it in this plan.
- **Cross-service verifier-CLI distribution test** — the verifier distribution (script + shared module + schemas + ABI, cryptography proven from a lockfile) is packaged and proven by a later task (R09); here only the fixed-path loading contract is in place (loader refuses ZIP/caller-chosen paths by construction).
- **Remote-registry network-error path → `unavailable`** — the registry is operator-mounted as a file today; the `unavailable` vocabulary and fail-closed behavior are tested via `registry=None` / unknown key, but no live network failure was injected (no remote fetcher exists yet).
- **JSON Schema validation of envelopes/registries** — the two schemas are consumable contracts for R06/R07/R09/R16; `jsonschema` is not in the pinned environment, so no automated schema-validation run was performed (fixture envelopes were validated by construction + behavioral tests).
- **Interop vectors for the X25519+HKDF+AES-GCM wrap** — round-trip + tamper tested; no cross-library (libsodium/age-style) test vectors, since both sides here use the same shared primitive by design.
- **Sub-second clock edges, TZ-variant registry documents, performance/load** — second-granularity boundaries tested per brief; load/perf is not in scope for a cryptographic-contract task.
