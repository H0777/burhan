## 1. What was verified (no code changed by the evidence round)

The four implementation commits were taken as-is and validated end-to-end on a disposable
PostgreSQL 16 container. **Zero implementation defects were found** — no fix commit was
needed. Key mechanisms verified:

- **`ai-engine/alembic.ini` + `app/db/migrations/env.py`** — migration URL comes
  EXCLUSIVELY from `MIGRATION_DATABASE_URL`; SQLite URLs are refused (protects the
  developer's `cyber_audit_chain.db`); `target_metadata` = live models;
  `python app/db/migrations/env.py stamp-if-matches` stamps a pre-existing database ONLY
  when `compare_metadata` shows zero drift, refuses (exit 2) an unknown/drifted schema
  with no `alembic_version` table left behind, and is idempotent when already stamped.
- **`app/db/migrations/versions/r11_baseline.py`** — revision `r11_baseline`,
  `down_revision = None`; creates all 17 tables with institutional FK/unique constraints
  and applies the PostgreSQL RLS section (ENABLE+FORCE+tenant policy on the 15
  institutional tables; explicit read-only `institutions_read_all` policy on the global
  `institutions` table).
- **`ops/postgres/init-roles.sql`** — idempotent, no passwords in file; provisions
  `ira_aml_migrator` (DB owner, migration role) and `ira_aml_app` (non-owner data-plane
  role), both `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOREPLICATION`; revokes
  schema CREATE from PUBLIC and the app role; grants app role DML+sequence-usage only,
  with `ALTER DEFAULT PRIVILEGES FOR ROLE ira_aml_migrator` so future migration-created
  objects inherit the same grants. **Invocation contract (from its own header, load-bearing
  — see §4 anomaly): `psql -d <db> -v db_name=<db> -f ops/postgres/init-roles.sql`.**
- **`app/db/session.py`** — `tenant_transaction(session, institution_id)` keeps its
  signature and uses `SELECT set_config('app.current_institution_id', :id, true)`
  (is_local=true, bindable — never `SET LOCAL` with a bind); commit on success, rollback
  on error, so a pooled connection is always reused context-free. `init_db()` on
  PostgreSQL only calls `verify_schema_revision()` (alembic_version must exist and equal
  the script-directory head; RuntimeError otherwise) — never `create_all`, never seed;
  `create_all`+demo seed are confined to the SQLite dev/demo path.
- **`app/db/models.py`** — `RLS_TABLES` (15 institutional tables) and
  `GLOBAL_POLICY_TABLES = {"institutions": ("institutions_read_all", "SELECT", ...)}`;
  the models-side enumeration mirrors the migration DDL.
- **Env hygiene** — no app source outside `app/db/migrations/` references
  `MIGRATION_DATABASE_URL` (scan covers `app/main.py`, config, session, routes, services,
  workers); the API boot path (settings + `init_db()`) runs against PostgreSQL with only
  the app-role `DATABASE_URL`.

## 6. MIGRATION CONVENTIONS (BINDING for R07, R08, R10, R12 and every later revision)

1. **Head is `r11_baseline`.** Every new revision MUST set
   `down_revision = "<current HEAD at merge time>"` — today that is `r11_baseline`;
   resolve the head AT MERGE TIME with `alembic heads`, never copy from an old task.
2. **Unique descriptive revision slugs** (like `r11_baseline`); slugs must be unique in
   the script directory. NEVER tie `down_revision` (or the slug) to plan task numbers
   (R07/R08/R10/R12 are task ids, not revisions).
3. **Never more than one head.** `alembic heads` must print exactly one revision before
   any merge; branching revisions are a review blocker.
4. **Migrations are the only schema authority on PostgreSQL.** No `create_all`, no
   ad-hoc DDL at runtime; production startup only verifies the revision
   (`verify_schema_revision`).
5. **Migration credentials** come exclusively from `MIGRATION_DATABASE_URL` (the
   `ira_aml_migrator` owner role). `alembic.ini` carries NO URL and NO secret; SQLite
   URLs are refused by `env.py`.
6. **New institutional tables** (e.g. R07/R08/R10/R12 tables) must: be added to
   `RLS_TABLES` in `app/db/models.py` AND the baseline-pattern RLS section of their
   revision (ENABLE+FORCE+`tenant_isolation_policy`), carry `institution_id` with a
   composite tenant FK and per-institution uniques, and never be owned by the app role.
   Global tables need an explicit policy like `institutions_read_all` — never "safe
   because no institution_id".
7. **App-role grants for new objects** flow from
   `ALTER DEFAULT PRIVILEGES FOR ROLE ira_aml_migrator` (already provisioned); if a
   revision creates objects under a different role, it must re-issue equivalent grants
   itself.

## 8. Anomalies / notes for the reviewer

- **One environmental failure occurred during evidence capture (not a code defect, and
  self-inflicted):** the FIRST invocation of `init-roles.sql` used
  `psql -U postgres -v db_name=<db>` **without `-d <db>`**, so psql connected to the
  default `postgres` database and the per-database grants/default-privileges landed there
  (`pg_default_acl` in `r11_test` was empty → first suite run: 3 passed / 8 failed, all
  failures the single class `psycopg.errors.InsufficientPrivilege: permission denied for
  table <x>`, exit 1). Re-running the script per its own header (`-d <db> -v db_name=<db>`,
  idempotent) fixed provisioning; the suite then passed 11/11 with no code change.
  Lesson recorded in §6: the `-d <db>` flag of the documented invocation is load-bearing.
- `requirements.txt` pins `alembic>=1.20.1` (floor, not `==`). This matches the file's
  existing convention (`psycopg[binary]>=3.1.0`); exact-pin tightening is an integration-
  lead decision, noted here for visibility.
- The `migration_owner_env_absent_from_api_process` boot snippet exercises the shared
  startup surface (settings + `init_db`) rather than importing `app.main` directly,
  because the v1 route modules referenced by `app/main.py` are uncommitted user edits that
  exist only in the main workspace; `app/main.py` itself IS inside the scanned source tree,
  so the env-var guarantee covers it (documented in the test docstring, commit `9d056df`).
