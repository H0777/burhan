## 1. What changed

- **`ai-engine/app/services/encrypted_object.py`** (new) — AES-256-GCM object envelope:
  - Fresh random 256-bit DEK per object (`os.urandom(32)`), wrapped FIRST via the R05 `KeyProvider.wrap_data_key` (X25519 + HKDF-SHA256 + AES-256-GCM) so the plaintext DEK never leaves the call frame unwrapped; only the wrapped form + `recipient_key_id` are returned for storage.
  - `compute_aad(institution_id, evidence_id, object_version)` — canonical-JSON AAD (R05 encoder) binding the three address dimensions. Any flip of any dimension changes the AAD and fails the GCM tag.
  - `encrypt_bytes` / `decrypt_bytes` — fail-closed: wrong key, tampered ciphertext/tag/nonce, or wrong AAD raise (`MissingKeyMaterialError` / `MalformedMetadataError` / `InvalidCiphertextError`) BEFORE any plaintext is returned.
- **`ai-engine/app/services/evidence_store.py`** (rewritten, `put`/`open` signatures preserved):
  - Layout: `<base>/<inst>/<evid>/v<n>/{object.bin, meta.json, COMMITTED.marker}`.
  - **Atomic no-replace publish**: content is staged in a UNIQUE staging dir (`.staging_v<n>_<uuid>`); the version directory name is claimed with `os.mkdir(exist_ok=False)` — the atomic no-replace primitive; there is NO exists-then-rename anywhere. Object + metadata are moved into the claim by the single owner; the `COMMITTED.marker` is `O_CREAT|O_EXCL`-written LAST. Readers refuse any version without the marker, so a crash can never expose a readable object. If anything fails after the claim but before the marker, the claiming writer rolls its own claim back (only the claim owner can — no other writer could have created it).
  - **Encryption at rest**: writes through a key-provider-backed store are `aes256gcm_v1` (ciphertext + base64 nonce/auth_tag/wrapped_dek/key_id in metadata); writes without a key provider are honestly labelled `legacy_plaintext_read_only` — never claimed encrypted.
  - **Path safety**: `validate_within_root` uses `Path.relative_to` (never string prefixes); symlinked AND junctioned components (junction = privilege-free Windows equivalent) are rejected BEFORE resolution in `_check_no_symlinks_below_root`; segment sanitization rejects traversal payloads.
  - **metadata `file_name`**: traversal payloads (`../x`, `..\x`, `sub/dir`, `..`, `....//`) are REJECTED (not sanitized); Arabic/Unicode display names are preserved in `display_name` + `metadata` while the on-disk internal id is forced ASCII.
  - **Size limit**: `25*1024*1024` enforced during streaming before any publication; a rejected object leaves no version dir, no metadata, no staging residue.
  - **Legacy reads**: pre-R06 flat layout (`v<n>_meta.json` + `v<n>_<file>`) reads as `legacy_plaintext_read_only` with SHA-256 verification — no silent conversion, no retroactive signing/encryption. `migrate_to_encrypted` creates a LATER encrypted copy that records `migration = {migrated_from_version, original_sha256, original_storage_format, migrated_at, provenance_level: "unchanged_from_original"}` at top level of the new version's metadata; the original bytes and provenance level stay untouched.
  - `open_verified_stream(institution_id, evidence_id, object_version) -> BinaryIO` — plaintext staged into a protected temp file inside the vault `.tmp/` (`O_CREAT|O_EXCL`, chmod 600 best-effort) only AFTER GCM-tag (or legacy-hash) verification succeeds.
  - `get_signed_manifest` — now produces a REAL R05 `SignedEnvelope` via `Signer.sign(DOMAIN_SERVICE_MANIFEST, body)`; body carries exactly the spec §6 fields (`institution_id, case_id, evidence_id, object_version, file_sha256, size, anchor_request_id, participant_id, issued_at, key_id`). No signer → refuse (never an unsigned or digest-named-signature manifest).
- **`ai-engine/app/services/evidence_broker.py`** — `EvidenceBroker(evidence_store, signer=None, key_provider=None)`:
  - Fail-closed: no signer AND no key material → `MissingSignerError` (an unsigned manifest is never emitted); with a key provider mounted on the store, the signer defaults to `Signer(key_provider)` (routes layer untouched — see §9).
  - `manifest_digest = envelope_digest(envelope)` — SHA-256 over the canonical SIGNED envelope; the Ed25519 signature itself is inside the digest input (proven by test: flipping ONLY the signature changes the digest and fails verification).
  - ONE transaction: EvidenceObject (with the signed envelope + encryption metadata) → EvidenceAnchor → CaseEvent → Outbox, one flush; the signed envelope row is flushed BEFORE the outbox event that references it is created. On DB failure the session rolls back as one unit and only unpublished staging is deleted; the already-published disk object remains as an ORPHAN for later-retention collection — this broker never deletes published evidence files.
- **`ai-engine/app/repositories/evidence_repository.py`** — `save_evidence_object` persists `storage_format, encryption_key_id, wrapped_dek (JSON), nonce, auth_tag, manifest_envelope_json, manifest_digest`; `encrypted` is now an HONEST flag: true only for `storage_format == "aes256gcm_v1"`.
- **`ai-engine/app/db/models.py`** — `EvidenceObject` gains the seven nullable columns above (legacy rows never retro-filled with fake crypto material).
- **`ai-engine/app/db/migrations/versions/0002_r06_evidence_crypto.py`** (new; slug `r06_evidence_crypto`, `down_revision = "r11_baseline"`) — see §6.
- **Tests**: new `ai-engine/tests/integration/test_evidence_immutability.py` (9 tests) and `test_evidence_encryption.py` (8 tests); updated `test_evidence_store.py` (fixture now mounts an institution key provider — tamper detection runs through the GCM gate) and `test_evidence_delivery.py` (broker wired to a real Signer; R06 assertions + 2 new tests).

## 2. Historical vulnerability context (why this task exists)

- The old store (T14) did exists-then-rename: two writers racing on the same version could BOTH "succeed" and silently overwrite each other's bytes (proven in RED below — `assert 2 == 1`, with the "winning" record even carrying cross-contaminated staging content). Disk presence alone is not WORM (spec §6).
- `evidence_repository` set `encrypted=True` on every row while the store wrote plaintext — a false claim under R18 honesty. R06 makes writes genuinely encrypted and corrects the flag for legacy rows in the migration backfill.
- `get_signed_manifest` returned a SHA-256 digest NAMED a signature. R06 emits a real Ed25519 `SignedEnvelope` via R05 primitives.

## 5. Envelope / digest semantics (spec §6, binding)

- Envelope: `{body, algorithm: "Ed25519", signature: base64}` produced by R05 `Signer.sign("AML_SERVICE_MANIFEST_V1", body)`; body fields exactly `institution_id, case_id, evidence_id, object_version, file_sha256, size, anchor_request_id, participant_id, issued_at, key_id` (+`schema_version` added by the Signer).
- `manifest_digest = sha256(canonical(signed envelope))` — `envelope_digest` from the shared module; the signature is part of the canonical document, so a signature-only change (identical body) changes the digest and fails registry verification (`test_manifest_digest_covers_signature`).
- Storage order: the EvidenceObject row carries `manifest_envelope_json` + `manifest_digest` and is flushed BEFORE `outbox_repository.enqueue_event` creates the referencing event; the outbox payload carries the exact stored envelope. On DB failure nothing persists (one transaction) and only staging is deleted; published-but-unanchored disk objects become orphans for LATER-retention collection — never deleted here.

## 8. Untested items / honest limits

- **KMS**: key custody stays behind the R05 `KeyProvider` interface (`LocalFileKeyProvider` in tests, seeded seed-files outside the vault); no real KMS was available — the interface isolation is exercised, a KMS implementation is not.
- **Multi-process WORM**: the no-replace guarantee rests on `os.mkdir` + `O_CREAT|O_EXCL` atomicity (POSIX + Windows NTFS). Two concurrent in-process writers are proven; independent PROCESSES on the same volume use the same OS primitives and are expected to hold, but a dedicated multi-process load test was not run. File-locking (mandatory locks / share modes) beyond the atomic-create primitives was not added — disk presence alone is still not legal WORM; the DB unique constraint `uq_evidence_object_version` remains the second enforcement layer.
- **Hard-crash residue**: a process killed BETWEEN staging and claim leaves a `.staging_*` directory behind; readers ignore it (never readable) and normal failure paths clean it, but automatic sweeping of another process's stale staging is future work (documented per brief: only unpublished staging is deleted by the owning failure paths).
- **Symlinks on this host**: symlink CREATION requires privilege (WinError 1314, no developer mode); the test creates a Windows **junction** instead (privilege-free, equivalent escape) and the store rejects both (`is_symlink()` + `is_junction()`). POSIX symlink behavior itself was not exercised on this Windows host.
- **Route layer untouched** (outside this task's file set): `app/routes/v2/evidence.py` still constructs `EvidenceBroker(evidence_store=store)`. With the broker now fail-closed, evidence upload works only where a key provider/signer is configured (the broker defaults its signer from a mounted store provider); keyless deployments get `MissingSignerError` instead of an unsigned manifest. Wiring the deployment's key mount + `set_evidence_store` provider is integration work for the deployment/identity lane; a keyless 500 today is honest refusal, not a silent downgrade.
- **`app.main`-dependent tests** (5 modules + 2 HTTP tests) could not run in this worktree for the pre-existing untracked `risk_scoring.py` reason (§4.3) — unaffected by R06 but unverified here.
- `open_verified_stream` temp files are chmod-600 best-effort; Windows ACL tightening is not applied.
