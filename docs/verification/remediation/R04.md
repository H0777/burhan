## 3. Deployment manifest v3 (DeploymentBinding) — `deployments/deployment-manifest.schema.json`

- `manifest_version: 3`; required fields: `deployment_id` (keccak over chain+MultiSig+finalize
  blockHash), `institution_id`, `chain_id`, `network`, `contract_version` (2.1.0, read from
  package.json), `status`, `deployed_at`, `deployed_at_block`, `confirmation_depth` (**2 on
  chain 31337**, 12 elsewhere), `deployer`, `bootstrap_finalized:true`, `addresses`,
  `deployed_code_hashes`, `governance` snapshot, `participants` (id/account/role/reason only).
- **Private keys are not valid fields**: schema `additionalProperties:false` +
  `patternProperties` ban for `private key/mnemonic/seed phrase` keys, plus a recursive
  `scanForbiddenKeys` pass in the verifier (belt and braces). Verified: 0 hits.
- `scripts/deploy.js` performs the full deploy→configure→bootstrap→finalize→invariant-assert
  sequence and writes the manifest **only after every step succeeded**, via temp file +
  fsync + atomic rename (`writeFileAtomic`). A failed bootstrap leaves no manifest for that
  run; a stale pre-existing manifest from an older deployment fails `verify-deployment`
  against the new chain (empty code at old addresses), so no valid manifest survives failure.
- Verifier (`scripts/verify-deployment.js`) validates the manifest against the schema
  (dependency-free draft-07 subset validator), then performs **real RPC checks**:
  chain id parity, per-contract `getCode` hash parity, `PROPOSAL_TTL=259200`,
  `TIMELOCK_DELAY=86400`, `requiredApprovals=2`, `isBootstrapFinalized`,
  `bootstrapAuthority=0`, roster (4+ eligible, ids→wallets binding, roles vs manifest),
  recorder/writer integration, `deployed_at_block ≤ head`.
