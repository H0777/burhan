## 1. What was fixed (F07 + binding acceptance criteria)

1. **F07 — the four case HTTP paths** (`create_case` / `list_cases` / `get_case_detail` / `transition_case`
   in `ai-engine/app/routes/v2/cases.py`) now run inside
   `with tenant_transaction(db, identity.institution_id) as session:` — the R10 signature
   `(session, institution_id)`. Pre-R12 they passed `identity` alone → `TypeError` on every authenticated call.
   The `/ {case_id}/evidence` route in the same file delegates to
   `_handle_upload_case_evidence`, which (merged R05/R06 work, `app/routes/v2/evidence.py:107`)
   already wraps its own `tenant_transaction(db, identity.institution_id)` — untouched, R06's lane.
2. **SQL compare-and-swap** (`case_repository.update_case_status(session, institution_id, case_id,
   expected_version, new_status, updates)` → `Case` or raises `CaseVersionConflict`):
   one atomic `UPDATE cases SET ... version = version + 1 ... WHERE institution_id = :inst
   AND id = :case AND version = :expected [AND status = :expected_status] RETURNING version, status,
   assigned_to_sub`. Zero rowcount → `CaseVersionConflict` (409). The pre-R12 "optimistic lock"
   was a Python read/compare — both racers passed it and both wrote. There is **no Python-only
   version check left** in the service: the SQL UPDATE is the only concurrency gate, and
   `expected_status` closes the state-machine TOCTOU. The case row, the append-only `CaseEvent`
   and the idempotency reservation are written in the SAME transaction (the route's
   `tenant_transaction`), so any failure rolls back all three.
3. **Semantic idempotency** (`case_service.py`): key scope =
   institution + sub + HTTP method + path + client key, hashed into the stored `key` column so the
   existing `uq_idempotency_inst_key (institution_id, key)` unique constraint reserves exactly that
   scope atomically; a concurrent same-key request loses the race at the constrained flush and gets 409.
   `request_hash` = canonical-JSON SHA-256 over ALL semantic fields — create:
   `{case_number, title, description, severity, assigned_to_sub}`; transition:
   `{case_id, action, expected_version, reason, new_assignee_sub}`. Same key + changed
   description/severity/new_assignee_sub → `IdempotencyConflictError` → **409**, never a stale success.
   TTL = 24 h: replay only while `expires_at > now`; expired entries are deleted and the request re-executes.
   Identical retries replay the stored response byte-for-byte (`response_json`) — no duplicate case, no duplicate event.
4. **Cursor pagination** (`GET /api/v2/cases`): stable keyset order `(created_at DESC, id DESC)`;
   the service fetches `limit+1` rows and emits `next_cursor` ONLY when the extra row exists
   (`next_cursor=None` exactly at exhaustion). The opaque cursor is base64(JSON `{"i": institution,
   "f": {status, severity}, "c": [created_at_iso, id]}`) and is **bound**: a cursor from another
   institution or without its filters → 400; garbage cursors → 400, never 500. Two additive optional
   query params `status` / `severity` were added to the list endpoint (the "filters" the cursor binds to).
5. **Error mapping** (routes): 401 unauthenticated; 403 no-membership / REGULATOR write / self-approval /
   unauthorized role; 404 unknown case; 409 `VersionConflictError`, `IdempotencyConflictError` and
   `InvalidTransitionError` (controller-mandated `invalid_transition_409`); 400 malformed cursor,
   missing reason, other `CaseServiceError`.
