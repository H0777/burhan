## 1. What changed

### 1.1 `contracts/access/RoleManager.sol` — institutional identity registry

A participant is now a **fixed institutional `bytes32` id** with exactly **one active wallet**.
Identity comes only from governance enrollment; it is never derived from a wallet address.

New/changed state:

- `struct Participant { address wallet; Role role; uint256 generation; bool enrolled; }`
- `mapping(bytes32 => Participant) private _participants;` + `bytes32[] _allParticipantIds;`
- `mapping(address => bytes32) private _participantIds;` — **permanent** wallet→id binding;
  rotated-away wallets keep their historical binding forever (forensic attribution) and can
  never be re-bound to another identity.

New functions (exact brief signatures):

| Function | Semantics |
|---|---|
| `enrollParticipant(bytes32 participantId, address wallet, Role role, string reason)` | governance-only; the ONLY identity-minting entry point. Rejects zero id (`"RoleManager: zero participant id"`), duplicate id (`"participant already enrolled"`), already-bound wallet (`"wallet already bound"`, retired wallets included), `Role.NONE`. Sets identity generation = 1. |
| `rotateParticipantWallet(bytes32 participantId, address newWallet, string reason)` | governance-only; retires the old wallet (role→NONE, binding kept) and moves the identity to `newWallet` with generation+1. Rejects unknown id, same wallet, already-bound new wallet. |
| `getActiveWallet(bytes32 participantId) -> address` | active wallet, or `address(0)` when unknown or the identity currently holds no role. |
| `countEligibleParticipants() -> uint256` | counts **distinct enrolled identities** with role SUPER_ADMIN or AUDITOR (OPERATOR/REGULATOR and the un-enrolled deployer never count). |

Changed behavior:

- **`assignRole` now requires enrollment**: target must be an enrolled identity's *active*
  wallet — `"RoleManager: target not enrolled"` / `"RoleManager: wallet not active for
  participant"` replace the old address-derived identity minting. Role changes bump the
  **identity-scope** generation (participant record + `_generations[activeWallet]` in lockstep).
- **`revokeRole`** keeps working for enrolled active wallets (identity binding survives, only
  privileges are removed; `getActiveWallet` returns `address(0)` while the identity is
  role-less) and for the deployer's temporary constructor role. Identity generation bumps.
- **Constructor no longer mints a participantId for the deployer** — the deployer's SUPER_ADMIN
  is explicitly temporary bootstrap privilege (dropped by `finalizeBootstrap`, see §1.2).

### 1.2 `contracts/access/MultiSigApproval.sol` — bootstrap & identity-scoped voting

- `bootstrapParticipants(bytes32[] _participantIds, address[] _wallets, uint8[] _roles, string[] _reasons)`
  — new mandated signature; the only bulk-entry point, itself bootstrap-gated, calling
  `roleManager.enrollParticipant` per entry (so a zero id / duplicate id / duplicate or retired
  wallet rolls back the **whole** enrollment).
- `finalizeBootstrap()` now requires `roleManager.countEligibleParticipants() >= 4`
  (`"MultiSig: need at least 4 eligible participants"`), verifies integration completeness +
  allowlists (AuditEngine integrated & referencing this MultiSig, recorder + evidence-writer
  set) **before** erasing `bootstrapAuthority = address(0)`, then **drops the deployer's
  temporary role** via the real governance path (`revokeRole`) unless the deployer wallet is an
  explicitly enrolled roster identity. After finalization `configureContracts` /
  `bootstrapParticipants` / `finalizeBootstrap` all revert (`onlyBootstrapAuthority` requires
  `!isBootstrapFinalized` and the authority is zeroed) — the authority cannot be resurrected.
- **Proposer identity binding**: `createProposal` records
  `_proposerParticipantIds[proposalId] = getParticipant(msg.sender).participantId`
  (`"MultiSig: proposer identity not enrolled"` guards the un-enrolled case);
  `approveProposal` rejects the proposer **by identity** — a person's rotated second wallet
  still reverts with `"MultiSig: proposer cannot approve own proposal"`.
- **Vote counting by identity**: voter = `getParticipant(msg.sender).participantId`; zero id
  cannot vote (`"MultiSig: caller identity not enrolled"`); inactive (rotated-away or revoked)
  wallets cannot vote (`"MultiSig: participant inactive"`, plus the pre-existing role gate);
  two wallets of one identity = ONE vote (`"MultiSig: participant has already voted"`).
  requiredApprovals stays 2 (independent non-proposer participants), TTL 24h (86,400s→
  configured as 24×3600 = 86,400 seconds; spec's 259,200s TTL value is R03/R04 config policy).

## 2. `getParticipant` tuple serialization (spec §5 shape preserved)

`getParticipant(address _addr) -> (bytes32 participantId, uint256 generation, Role role, bool active)`

ABI serialization: a 4-tuple `(bytes32, uint256, uint8, bool)` — head 4×32 bytes, no dynamic
data; ethers v6 returns it as a `Result` (`participantId` lowercase-hex `bytes32` string,
`generation` bigint, `role` number, `active` boolean). Exact semantics by wallet class:

| Wallet class | participantId | generation | role | active |
|---|---|---|---|---|
| Active wallet of an enrolled identity | the institutional id | identity's current generation | identity's current role | `role != NONE` |
| Rotated-away (retired) wallet | the **same historical id** (attribution kept) | the wallet's stale generation snapshot | `NONE` | `false` |
| Un-enrolled address (incl. the deployer before finalization) | `bytes32(0)` | the address's local generation | raw role mapping | `role != NONE` |
| Unknown address (default) | `bytes32(0)` | `0` | `NONE` | `false` |

The un-enrolled/unknown rows intentionally reproduce the pre-R02 behavior so existing callers
(frontend, GovernanceExecution flows) only see *added* identity data for enrolled wallets, and
the deployer tuple still reads sanely while its temporary role is live.

## 3. New / changed events (all carry participantId + generation)

```text
ParticipantEnrolled(bytes32 indexed participantId, address indexed wallet, Role indexed role,
                    uint256 generation, address enrolledBy, string reason, uint256 timestamp)
WalletRotated(bytes32 indexed participantId, address indexed oldWallet, address indexed newWallet,
              uint256 generation, string reason, uint256 timestamp)
RoleAssigned(address indexed target, Role indexed newRole, address indexed assignedBy,
             string reason, uint256 timestamp, bytes32 participantId, uint256 generation)   // +2 fields
RoleRevoked(address indexed target, Role indexed previousRole, address indexed revokedBy,
            string reason, uint256 timestamp, bytes32 participantId, uint256 generation)   // +2 fields
```

`WalletRotated.generation` is non-indexed (Solidity caps indexed event args at 3); the
deployer's constructor `RoleAssigned` emits `participantId = bytes32(0)`, `generation = 1`.
MultiSigApproval events are unchanged in shape (`BootstrapFinalized(uint256)`,
`ParticipantsBootstrapped(uint256)` now counts wallets enrolled).
