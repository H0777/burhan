## 1. What changed

### 1.1 MultiSigApproval — the single decision point (spec §4/§6/§7)

- **Closed action table** (`_validateAndSchedule` + per-type validators, §5 below): every
  `createProposal` must carry a (proposalType, target, selector) triple from the fixed
  table; targets are ONLY the contract addresses registered at `configureContracts` time.
  `setGovernance` is on NO list → governance migration is unreachable through the coordinator.
- **Decode + re-encode**: calldata is decoded with the exact ABI types and re-encoded;
  digest comparison of the re-encoding vs the original bytes rejects trailing garbage and
  malformed encodings (`"MultiSig: malformed action data"`).
- **Timelock**: `TIMELOCK_DELAY = 86,400s` for POLICY_CHANGE, ROLE_CHANGE, SYSTEM_CONFIG
  grants (`authorized=true`) and `setBusinessHours`; **delay 0** for OVERRIDE_WARNING,
  EMERGENCY_UNPAUSE and SYSTEM_CONFIG revocations (`authorized=false`) — quorum (2
  independent approvals) still required in every case. `PROPOSAL_TTL = 259,200s` for ALL
  types; execution at `now >= expiresAt` fails (`approveProposal` also enforces expiry).
  The constructor no longer takes a TTL parameter — the TTL is a fixed protocol constant.
- **actionHash** binds `chainId, governance address, proposalId, proposalType, target,
  keccak256(data), createdAt, notBefore, expiresAt`.
- **Identity + generation at vote time**: proposer identity AND generation stored at
  creation; each voter's identity AND generation stored at approval. Execution re-checks:
  status/quorum, `now >= notBefore`, `now < expiresAt`, proposer eligibility at the recorded
  generation (a proposer generation change forces a new proposal), and every recorded
  voter's eligibility at their vote-time generation — resolved via each identity's
  **CURRENT active wallet** (`roleManager.getActiveWallet`) + `_isEligibleAtGeneration`
  (enrolled, active, SUPER_ADMIN/AUDITOR, generation equal). Fail-closed.
- **Permissionless execution**: `executeProposal` no longer requires `onlyAuthorized` —
  the executor adds no vote and creates no decision; all authorization is re-checked from
  the recorded state. Only the bytes stored at creation are executed, once.
- **Override conflict-of-interest**: parties are read from `AuditEngine.getTransaction`
  (the engine's own record), never from proposer fields; at creation the decoded
  sender/receiver must match the record (`"AuditEngine: transaction party mismatch"`) and
  the proposer identity must not be a party (`_identityIsParty` — retired wallets keep the
  identity, so a rotated wallet stays blocked). At approval the same identity-scoped check
  runs against the engine record.
- **Atomic target execution**: on target revert the whole transaction reverts, the proposal
  stays APPROVED (not EXECUTED, not consumed) and remains executable until expiry — pinned
  by `emergency_epoch_replay` (stale-epoch proposal reverts, isPaused unchanged, status
  APPROVED) and the converted GovernanceExecution atomicity test.
- **rejectProposal identity-scoped** (carried pointer 1): participantId-keyed vote dedup,
  proposer blocked (`"MultiSig: proposer cannot reject own proposal"`), enrolled+active
  caller required — same gate structure as `approveProposal`.
- **`GOVERNANCE_CONFIG` → `SYSTEM_CONFIG`** enum member (index 4 unchanged).
- `createProposal` 4th parameter is now a `string description` (was `bytes32 reasonHash`);
  `ProposalCreated` carries the description string; `LegacyProposalCreated` event and the
  mutable `proposalTTL` state variable removed.

### 1.3 ForensicTrail — التزام البيان (manifest commitment) + case references

- `submitEvidenceAttested(uint256 incidentId, bytes32 requestId, bytes32 typeHash,
  bytes32 descriptionHash, bytes32 fileSha256, bytes32 manifestDigest) -> uint256`:
  the `requestId -> manifestDigest` map is written in the SAME transaction that appends
  the evidence; emits `EvidenceManifestAnchored(bytes32 indexed requestId, uint256
  indexed evidenceId, bytes32 manifestDigest)`. Zero digest rejected; same requestId with
  a different digest = conflict rejected; same requestId + same digest is idempotent
  (returns the original evidenceId, evidence count unchanged, no event). No backfill:
  a requestId already consumed by the unattested path can never gain a commitment
  (`"ForensicTrail: requestId already used"`). The commitment is NOT part of the Evidence
  V2 entry hash (schema untouched — see §4 verification).
- `getManifestDigest(bytes32) -> bytes32` (0 = none).
- `createIncidentForCase(bytes32 caseReferenceHash, bytes32 titleHash, bytes32 severityHash)
  -> uint256` + `getIncidentByCaseReference(bytes32) -> uint256`: contract-institution-wide
  references; the FIRST registration keeps metadata and creator; a later request (any
  authorized writer) with the same metadata returns the SAME incident (no takeover);
  different metadata reverts (`"ForensicTrail: case reference metadata conflict"`).
  `caseReferenceHash = keccak256(abi.encode(chainId, ForensicTrail, institutionRefHash,
  caseIdHash))` is computed OFF-chain by the caller (opaque to the contract).
- Old `submitEvidence` STAYS for the automated AuditEngine alarm path
  (`chain_generated_unattested`, classified by R07) — pinned by `automated_alarm_still_records`.
- `submitEvidence` body refactored into a shared `_appendEvidence` core (behavior identical).

## 3. Carried-pointer decisions (from the R02 review)

1. **rejectProposal identity-scoping** — implemented exactly as `approveProposal`:
   participantId-keyed (`_hasVotedParticipant`), enrolled+active caller required,
   proposer blocked from rejecting their own proposal, expiry enforced. New regression:
   MultiSigApproval.test.js "Should block the proposer from rejecting their own proposal".
2. **Mid-proposal wallet rotation** — chosen handling: execution re-validation is
   **identity-scoped via each participant's CURRENT active wallet** (`getActiveWallet`)
   compared against the vote-time **generation snapshot**. The dead wallet address is
   never consulted, so the check is no longer hostage to a retired address's storage;
   but a rotation bumps the identity's generation, so the vote recorded under the retired
   key fails the generation conjunct and the proposal cannot execute — **fail-closed by
   design** (stale authorization never executes; the retired key is presumed suspect,
   which is why rotation exists). A rotation mid-proposal therefore requires a fresh
   proposal after the rotation; the old proposal simply expires at TTL instead of
   executing. Pinned by `proposer_rotation` and the R02 `ParticipantIdentity` suite.
3. **Stale-generation companion (assignRole-driven)** — added as
   `stale_generation_after_approval` in `test/security/TimelockAndActionBinding.test.js`:
   the approver stays ACTIVE and ELIGIBLE (AUDITOR → SUPER_ADMIN via a governance
   ROLE_CHANGE proposal); only the generation conjunct changes, and execution reverts
   with `"MultiSig: approver authorization generation is stale or revoked"`.
